1. WHAT THIS IS AND WHY IT EXISTS
================================================================================

The wider programme (see PROJECT_BRIEF.md) is an AI-native healthcare platform
whose centrepiece is an "Agentic Admin CMS". Management redirected the team away
from building that CMS from scratch, and asked instead for a working proof of
concept on Payload CMS 3.x.

The POC exists to demonstrate four specific claims to management:

  1. A structured admin dashboard with real relations between clinical entities.
  2. Built-in drafts and version history on clinical content.
  3. A public Next.js page server-rendered from Payload's Local API.
  4. Instant, repeatable mock-data seeding.

It is a DEMO ARTIFACT, NOT PRODUCTION. Every decision below optimises for
"nothing breaks during a live walkthrough" over production fidelity. Where that
trade-off was made, it is flagged so it can be defended in the room.

The agentic subagent harness and the human-verification access-control design
(researched separately, earlier in this project) are deliberately OUT OF SCOPE
here. They remain verbal roadmap talking points — see section 16.

5. ARCHITECTURAL DECISIONS AND RATIONALE
================================================================================

5.1  DATABASE: SQLite, not Dockerised PostgreSQL
--------------------------------------------------------------------------------
Adapter: @payloadcms/db-sqlite (Drizzle ORM + libSQL)
Database file: clinic-poc/clinic.db

Chosen over Docker Postgres for these reasons:

  - No daemon. Nothing to start, no port conflicts, no container healthcheck
    wait, no compose file to go wrong thirty seconds before a demo.
  - Drizzle's `push` mode is on by default in development, so schema changes
    sync from the Payload config with no migration step while iterating.
  - Resetting is `rm clinic.db` (or restoring the backup copy).
  - The .db file is portable, so a known-good pre-seeded state can be kept as a
    safety net.

Trade-offs — state these before management asks:

  - SQLite does not support Payload's Point (geo) field. Irrelevant here; there
    is no mapping in scope.
  - Production would use PostgreSQL. The change is the adapter import plus
    generated migrations — roughly a three-line config change. This choice does
    NOT paint the project into a corner. Say so proactively, because it is the
    obvious challenge.
  - Known ecosystem risk: @libsql native binaries have historically conflicted
    with Turbopack on some platforms. In practice this did NOT occur here —
    Next 16 runs Turbopack by default and the dev server boots in ~1.6s. If it
    ever does bite, run `next dev --webpack`, or fall back to Docker Postgres.

5.2  TAILWIND CSS SCOPING — the single most important implementation detail
--------------------------------------------------------------------------------
Tailwind's preflight layer resets base element styles globally and WILL visibly
break the Payload admin panel if it leaks into it.

The fix is route-group separation:

  - `@import 'tailwindcss'` appears ONLY in src/app/(frontend)/styles.css
  - That file is imported ONLY by src/app/(frontend)/layout.tsx
  - Nothing Tailwind-related touches src/app/(payload)/ or custom.css

This works because Payload's blank template has NO shared root layout — each
route group renders its own <html> and <body>. The two style worlds never meet.

VERIFIED: the admin dashboard renders correctly with Tailwind installed.

If anyone adds a src/app/layout.tsx importing global CSS, the admin will break.

5.3  PLAIN <img> RATHER THAN next/image
--------------------------------------------------------------------------------
Payload serves media through its own /api/media/file/** route, and the
components already request the correctly-sized generated variant. next/image
would add configuration failure modes (loader config, local/remote patterns) for
no measurable benefit at POC scale. Both grid components carry a comment
explaining this, and a local eslint-disable for the no-img-element rule.
Revisit when Core Web Vitals are actually being measured.

5.4  force-dynamic ON THE LANDING PAGE
--------------------------------------------------------------------------------
The landing page sets `export const dynamic = 'force-dynamic'`.

Without it, Next.js caches the render and the central demo beat — publish in the
admin, refresh the site, watch content appear — silently fails. Correct for a
POC. Production would use ISR plus on-demand revalidation triggered from an
`afterChange` hook rather than opting out of caching entirely.

5.5  SUBFOLDER LAYOUT
--------------------------------------------------------------------------------
The app lives in clinic-poc/ rather than at the repository root, because the root
already holds the strategy documents (PROJECT_BRIEF.md, this file). Keeps
research artefacts and application code cleanly separated.

  Its admin config pins its own columns:
      defaultSort: 'name'
      defaultColumns: ['name', 'specialization', 'yearsExperience', '_status']

8. ACCESS CONTROL — ONE RULE, THREE ENFORCEMENT POINTS
================================================================================

src/access/index.ts holds three functions:

  anyone                     () => true
  authenticated              ({ req: { user } }) => Boolean(user)
  publishedOrAuthenticated   ({ req: { user } }) =>
                               user ? true : { _status: { equals: 'published' } }

The third is the important one. It returns a WHERE QUERY, not a boolean. The
constraint is merged into the database query itself, so unpublished clinical
content is never loaded — it is not merely hidden in the UI.

The same three functions govern:

  1. The admin panel
  2. The REST and GraphQL APIs
  3. The server-rendered public page

...because the landing page calls the Local API with `overrideAccess: false`.

  *** IMPORTANT FOOTGUN ***
  Payload's Local API defaults `overrideAccess` to TRUE, which BYPASSES ALL
  ACCESS CONTROL. Any code calling payload.find/create/update without passing
  `overrideAccess: false` (and a user) silently ignores every rule above.
  The landing page passes `false` explicitly, so it runs as an anonymous
  visitor. This gives one source of truth for draft-hiding instead of two that
  can drift apart. Lint for this pattern as the codebase grows.

Observable proof of the rule working: on the public site, General Medicine
displays "1 CONSULTANT" even though it has two doctors — the second is a draft.
The access rule reaches inside the join field's count.

9. PUBLIC SITE
================================================================================

A single page at src/app/(frontend)/page.tsx composed of four sections:

  Hero                teal gradient, clinic name, live department and consultant
                      counts, two CTAs, nav that collapses below the sm
                      breakpoint
  DepartmentGrid      responsive card grid; card image (generated `card` size),
                      emoji badge, title, summary, and consultant count taken
                      from the join field's totalDocs
  DoctorDirectory     consultant cards — avatar or initials fallback, name,
                      specialization, qualifications, department badge with
                      emoji, years-experience badge, availability badges
  InquiryForm         client component, server action submission
  Footer              copyright plus a link through to /admin

Data fetching (the architecturally significant part):

  const payload = await getPayload({ config })
  const [departmentsResult, doctorsResult] = await Promise.all([
    payload.find({ collection: 'departments', depth: 2, limit: 12,
                   sort: 'title',  overrideAccess: false }),
    payload.find({ collection: 'doctors',     depth: 2, limit: 24,
                   sort: 'name',   overrideAccess: false }),
  ])

  - No HTTP round trip. The Local API runs in-process against the database.
  - depth: 2 populates the image/avatar uploads, the department relationship,
    and the joined doctors.
  - Both queries run concurrently.

AVAILABILITY BADGES
  Derived from the structured consultationHours array, not stored separately:
    - Green "Available today" pill when a slot matches the current weekday
    - Grey "By appointment" pill otherwise
    - Per-day chips ("Mon 09:00–13:00"), with the current day's chip
      highlighted in brand colour
  This makes the structured data visibly do something rather than just sit in
  the admin panel.

STYLING
  Tailwind v4, CSS-first (no tailwind.config.ts). A custom `brand` teal palette
  (50..900) is declared with the @theme directive in styles.css, plus a system
  font stack.

INQUIRY SUBMISSION FLOW
  InquiryForm.tsx ('use client') uses React's useActionState for pending,
  success and error states, and posts to submitInquiry in actions.ts.

  The server action:
    - validates server-side (name >= 2 chars, email regex, message >= 10 chars)
    - returns per-field errors that render beneath the offending input
    - on success writes via payload.create({ collection: 'inquiries', ... })
    - replaces the form with a green "Enquiry received" confirmation panel

  No client-side validation library, no API route.

14.1  BUG FOUND AND FIXED: "<No Department>" in the join table
--------------------------------------------------------------------------------
The join field table on a Department page showed a "Department" column reading
"<No Department>" on every row. The join table inherits the target collection's
admin.defaultColumns — which for Doctors includes `department` — and that
relationship is not populated inside the join context, so it rendered empty. The
column is redundant there anyway, since every row belongs to that department.

Fixed in src/collections/Departments.ts by giving the join its own columns:

    defaultSort: 'name',
    admin: {
      defaultColumns: ['name', 'specialization', 'yearsExperience', '_status'],
    }

Now reads: Name | Specialization | Years Experience | Status, name-sorted.
Worth catching — an empty column is exactly what a manager stops a demo to ask
about.

14.2  create-payload-app REQUIRES AN INTERACTIVE TERMINAL
--------------------------------------------------------------------------------
`npx create-payload-app` failed with:
    TTY initialization failed: uv_tty_init returned EBADF

There is also NO `--db` flag — the database choice is an interactive prompt. The
documented CLI options are only -n (name), -t (template), -e (example),
-a (coding agent), --use-npm/yarn/pnpm/bun, --no-deps and -h.

Workaround: the official blank template was obtained by sparse checkout of the
payloadcms/payload repository instead, then adapted (SQLite adapter, pinned
versions, clinic collections).

14.3  THE main-BRANCH TEMPLATE IS AHEAD OF THE PUBLISHED PACKAGES
--------------------------------------------------------------------------------
*** The most valuable finding here for anyone else on the team. ***

The first attempt produced HTTP 500 on /admin. The template pulled from the
repository's `main` branch imported symbols that do not exist in the published
3.88.0 packages:

    HierarchyField              not in @payloadcms/ui@3.88.0
    HierarchyButton             not in @payloadcms/ui@3.88.0
    HierarchySidebarTabServer   not in @payloadcms/ui@3.88.0
    generatePayloadViewport     not in @payloadcms/next@3.88.0

The `main` template tracks unreleased work. Resolved by taking the template from
the v3.88.0 tag so template and packages match.

LESSON: never scaffold from templates/blank on `main` while installing published
package versions. Match the tag to the installed version.

14.4  NODE ENGINE MISMATCH
--------------------------------------------------------------------------------
The template's package.json declared `node: >=24.15.0` while the machine runs
v22.22.1. Node 22.22.1 genuinely satisfies Next 16's real requirement, so the
engines field was relaxed to `>=22.11.0`. (.npmrc contains only
legacy-peer-deps=true, no engine-strict, so this was a warning rather than a
hard failure — but it was relaxed to keep installs quiet.)

15. KNOWN LIMITATIONS AND DELIBERATE OMISSIONS
================================================================================

IN SCOPE and working:
  public content management, editorial workflow with drafts and version history,
  patient inquiry capture and triage.

DELIBERATELY NOT IN SCOPE:
  - Patient records / PHI of any kind
  - Appointment booking or calendar integration
  - Patient-facing logins
  - Department detail pages (/departments/[slug])
  - Email delivery (Payload warns "No email adapter provided. Email will be
    written to console." — expected, nothing is sent)
  - Any AI or agentic functionality
  - Automated tests

  *** WHY PHI IS EXCLUDED BY DESIGN — say this explicitly in the walkthrough ***
  If patient names, symptoms or appointment details were written into Payload
  collections, THE ENTIRE CMS DATABASE would fall into HIPAA scope: audit
  controls, encryption at rest, a signed BAA, breach notification, the whole
  surface. The CMS holds only public marketing content. Booking and patient
  data belong in a separate PHI-scoped service, with the CMS storing at most an
  opaque booking reference.

OTHER LIMITATIONS TO BE AWARE OF:
  - Payload itself holds no SOC 2 Type II, ISO 27001 or HIPAA BAA. Self-hosting
    moves that responsibility to the cloud provider, which is why the PHI
    boundary above matters.
  - Roles are code, not a clickable UI. Access control lives in
    src/access/index.ts and moves through pull requests. Good for auditability;
    clinic staff cannot self-manage permissions.
  - There is no approval-workflow engine. Drafts, versions and access control
    give the ENFORCEMENT; a review queue, dual editorial/clinical sign-off and
    provenance display would be custom admin views.
  - Emoji department icons rendered as placeholder boxes in the headless test
    browser. This is a font matter, not a code one, and they should render
    correctly in real Chrome on Windows — but LOOK AT THE PAGE IN YOUR OWN
    BROWSER before the demo to confirm.
  - Not a git repository yet.

16. LIVE WALKTHROUGH SCRIPT
================================================================================

Roughly 12 minutes. Run `pnpm seed` first for a clean dataset.

STRUCTURE (2 min)
  [ ] Log into /admin. Dashboard shows collections grouped
      Clinic / Patients / System.
  [ ] Departments -> open Cardiology -> scroll to the Doctors table.
      Say: "Doctors own this relationship. The department surfaces them
      automatically — no duplicated data, no custom code."
  [ ] Open a doctor. Point out the department relationship, the repeatable
      consultation-hours rows, the avatar.

EDITORIAL SAFETY — the headline (4 min)
  [ ] Create a new doctor. Save as DRAFT. Show _status "draft" in the list.
  [ ] Switch to the public site. It is not there.
      Say: "Unreviewed clinical content cannot reach patients."
  [ ] Publish. Refresh the site. It appears.
  [ ] Edit a published doctor's bio, save. Open the Versions tab. Show the
      diff. Restore the previous version. Refresh the site — it reverts.
      Say: "Every change to clinical content is attributable and reversible."

PUBLIC SITE (2 min)
  [ ] Landing page: hero, departments grid, consultant cards with availability
      badges — all server-rendered from the same database, with no separate API
      service to deploy or secure.
  [ ] Narrow the browser to mobile width. Grids collapse cleanly.

ROUND TRIP (2 min)
  [ ] Submit the inquiry form as a patient. Refresh the admin. The enquiry is
      there with status "new". Change it to "contacted".

ENGINEERING CREDIBILITY (2 min)
  [ ] Open src/payload-types.ts. Types are generated from the schema, and the
      page component consumes them.
  [ ] Log out. Hit /api/inquiries -> 403. Hit /api/departments -> published
      only. Say: "One access rule, enforced across the admin, the REST API and
      the server-rendered page."
  [ ] Run `pnpm seed`. The whole clinic rebuilds in about seven seconds.

FRAMING — say these out loud
  [ ] In scope: public content management, editorial workflow, patient enquiries.
  [ ] Not in scope, by design: patient records, booking, patient logins —
      because PHI in the CMS would pull the entire database into HIPAA scope.
  [ ] Production path: SQLite -> PostgreSQL plus migrations (a three-line
      adapter change).
  [ ] Roadmap: per-agent scoped API keys via Payload's official MCP plugin;
      draft-only agent identities, with the restriction declared once on the
      collection so it applies to every route in rather than being repeated
      per endpoint; dual editorial + clinical sign-off for medical claims.

17. PATH TO PRODUCTION
================================================================================

Ordered by dependency, not by effort.

  1. git init, commit, push. Nothing is version controlled yet.
  2. Swap SQLite for PostgreSQL: change the adapter import in payload.config.ts,
     generate migrations, and stop relying on Drizzle push.
  3. Decide and document the PHI boundary before any booking work starts. This
     is the single most consequential architectural decision remaining.
  4. Move media off local disk to S3 or equivalent via a cloud-storage adapter
     plugin; local staticDir will not survive a containerised deploy.
  5. Add an email adapter for password reset and enquiry notifications.
  6. Replace force-dynamic with ISR plus on-demand revalidation from an
     afterChange hook.
  7. Add automated tests. The template's Playwright and Vitest harness was
     removed and can be restored from the v3.88.0 template.
  8. Harden auth: real password policy, login-attempt lockout tuning, and a
     considered role model beyond the single admin.
  9. THEN, and only then, the agentic layer: per-agent Payload users, scoped
     API keys through the MCP plugin, draft-only access control for agent
     identities, provenance tainting for anything derived from untrusted
     external sources, and a review-queue admin view with dual sign-off.
